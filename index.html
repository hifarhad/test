Q1. Rewrite this classic loop using modern ABAP constructor expressions and a single statement. Return only rows where amount > 100, sorted descending by amount.

DATA: lt_in  TYPE STANDARD TABLE OF ty_item,
      lt_out TYPE STANDARD TABLE OF ty_item.

LOOP AT lt_in INTO DATA(ls).
  IF ls-amount > 100.
    APPEND ls TO lt_out.
  ENDIF.
ENDLOOP.
SORT lt_out BY amount DESCENDING.
Show answer 
DATA(lt_out) =
  VALUE ty_items(
    FOR ls IN lt_in
      WHERE ( amount > 100 )
      ( ls ) ).

SORT lt_out BY amount DESCENDING.
Examiner's view: FOR ... WHERE inside VALUE is the expected answer. Sorting still needs a separate SORT (or use REDUCE + INSERT ... INDEX 1 if you want it truly single-statement, but that hurts readability). Naming: ty_items must be a table type of ty_item.

Q2. You need the total and average amount from an internal table in one pass, plus a count. Write the modern ABAP expression. Name the structure fields explicitly.

Show answer 
TYPES: BEGIN OF ty_stat,
         count   TYPE i,
         total   TYPE p LENGTH 15 DECIMALS 2,
         average TYPE p LENGTH 15 DECIMALS 2,
       END OF ty_stat.

DATA(ls_stat) =
  REDUCE ty_stat(
    INIT sum TYPE p LENGTH 15 DECIMALS 2
         cnt TYPE i
    FOR ls IN lt_items
    NEXT sum = sum + ls-amount
         cnt = cnt + 1 ).

ls_stat-count   = cnt.
ls_stat-total   = sum.
ls_stat-average = COND #( WHEN cnt > 0 THEN sum / cnt ELSE 0 ).
Examiner's view: A common trap is trying to compute average inside REDUCE NEXT — you can't divide by a counter that's still accumulating. Compute it after the reduction. Also note COND guards against division by zero.

Q3. Convert a string '2026-09-26' to a proper dats date and back to ISO format. Show both directions using modern syntax.

Show answer 
DATA(lv_str)  = '2026-09-26'.
DATA(lv_date) = CONV dats( lv_str ).   " implicit, no separators -> '20260926'

" Safer explicit conversion when separators exist:
DATA(lv_date2) = CONV dats( replace( val  = lv_str
                                     sub  = '-'
                                     with = '' ) ).

" Back to ISO:
DATA(lv_iso) = |{ lv_date2 DATE = ISO }|.   " -> '2026-09-26'
Examiner's view: The string template option { ... DATE = ISO } is the expected modern approach. Watch out: CONV dats( '2026-09-26' ) actually fails at runtime because of the hyphens — that's the trap in this question.

Q4. Write a CDS view entity that returns SalesOrder, SalesOrderItem, Product, OrderQuantity, and NetAmount from the standard sales item table, filtered to items with quantity > 0, exposed for OData.

Show answer 
@AccessControl.authorizationCheck: #NOT_REQUIRED
@EndUserText.label: 'Sales Order Items'
@ObjectModel.supportedCapabilities: [ #SQL_BASED_VIEW ]
define view entity ZI_SalesOrderItem
  as select from I_SalesOrderItem
{
  key SalesOrder,
  key SalesOrderItem,
      Product,
      OrderQuantity,
      NetAmount,
      @Semantics.currencyCode: true
      TransactionCurrency
}
where OrderQuantity > 0
Examiner's view: Use define view entity (not the deprecated define view). Both key fields must be marked key. If you expose amounts, you must also expose the currency code with @Semantics.currencyCode: true — forgetting this is a classic deduction.

Q5. You need a view that joins a header and an item table. Explain when you would use an association instead of a JOIN, and give the syntax skeleton.

Show answer 
define view entity ZI_OrderWithItems
  as select from ZI_OrderHeader as h
    association [1..*] to ZI_OrderItem as _Items
      on h.OrderId = _Items.OrderId
{
  key h.OrderId,
      h.Customer,
      h.Currency,
      _Items
}
Examiner's view — when to use which:
  • Association: lazy evaluation (only fetched if the consumer requests it), reusable across views, needed for RAP, supports path expressions, keeps cardinality explicit.
  • JOIN: eager, flattened result at DB level, good for pure reporting with no reuse and no composition semantics.
  • For RAP business objects, associations are mandatory — joins won't give you the composition tree.

Q7. You are defining a managed RAP business object. Write the behavior definition for an entity with create, update, delete, and a validation that OrderQuantity > 0. Include draft handling.

Show answer 
managed implementation in class zbp_i_orderitem unique;
strict ( 2 );
with draft;

define behavior for ZI_OrderItem alias OrderItem
  persistent table zorderitem
  draft table zorderitem_d
  etag master LastChangedAt
{
  create;
  update;
  delete;

  field ( readonly ) OrderId, OrderItem;

  validation validateQuantity on save { field OrderQuantity; }

  draft action Activate optimized;
  draft action Discard;
  draft action Edit;
  draft action Resume;
}
Examiner's view: For a managed BO you need: managed, strict ( 2 ), with draft, persistent table, draft table, and the four standard draft actions. The validation references on save here — for field-level checks on save vs on modify matters.

Q8. Write the ABAP class implementation for the validation from Q7. Include the message definition.

Show answer 
" Message class Z_ORDER_MSG, message 001: 'Quantity must be greater than zero'

CLASS zbp_i_orderitem DEFINITION PUBLIC ABSTRACT FINAL
  FOR BEHAVIOR OF zi_orderitem.
ENDCLASS.

CLASS zbp_i_orderitem IMPLEMENTATION.
  METHOD validateQuantity.
    READ ENTITIES OF zi_orderitem IN LOCAL MODE
      ENTITY OrderItem
        FIELDS ( OrderQuantity )
        WITH CORRESPONDING #( keys )
      RESULT DATA(lt_items).

    LOOP AT lt_items INTO DATA(ls_item).
      IF ls_item-OrderQuantity <= 0.
        APPEND VALUE #( %tky = ls_item-%tky ) TO failed-orderitem.
        APPEND VALUE #(
          %tky        = ls_item-%tky
          %msg        = new_message(
                          id       = 'Z_ORDER_MSG'
                          number   = '001'
                          severity = if_abap_behv_message=>severity-error )
          %element-OrderQuantity = if_abap_behv=>mk-on
        ) TO reported-orderitem.
      ENDIF.
    ENDLOOP.
  ENDMETHOD.
ENDCLASS.
Examiner's view: The three things examiners look for: (1) IN LOCAL MODE read, (2) appending to both failed- and reported- tables, (3) using new_message( ) with proper severity. Forgetting %element- means the message won't attach to the field in the UI.
RAP~5%

Q9. Explain the difference between a determination and a validation in RAP, and when each runs. Give one use case for each.

Show answer
Determination
  • Computes or fills data automatically. Runs on on save, on modify, or on prepare.
  • Use case: auto-fill CreatedBy, CreatedAt, or calculate NetAmount = Quantity × Price.
  • Never fails — it only sets values.
Validation
  • Checks data against business rules. Runs on save or on modify.
  • Use case: reject quantity <= 0, or reject a delivery date in the past.
  • Produces messages and can block the save (severity-error).
Memory hook: Determination writes, Validation guards.

Clean Core~5%

Q10. A customer wants to add a custom field to the standard sales order UI without modifying SAP code. Name the correct extensibility approach and outline the steps.

Show answer
Approach: In-app extensibility (key-user extensibility) + developer extensibility.
  1. Custom field: create via Custom Fields and Logic app (in-app) or ABAP Development Tools with a custom CDS view extension.
  2. Extend the CDS view: use extend view entity with an association to your custom table, rather than copying the SAP view.
  3. Extend the RAP BO: use extend behavior to add validations/determinations on the standard BO.
  4. UI: add the field via the Adapt UI capability, no code change to SAP screens.
Why not a modification? Modifications break the clean core, block upgrades, and aren't allowed in ABAP Cloud (language version ABAP for Cloud Development).
ABAP Cloud~5%

Q11. Which of these statements about ABAP for Cloud Development is true, and why? Explain each. (a) You can use any function module. (b) You can use CALL FUNCTION to a released API. (c) You can use SELECT on any table. (d) You can use WRITE statements.

Show answer
Only (b) is correct — with a caveat.
  • (a) False. Only released APIs (C1 contract) are allowed. Unreleased FMs are blocked by the syntax check.
  • (b) True. You may call released function modules, but the modern preference is to call released classes / CDS-based APIs. Many classic FMs are not released.
  • (c) False. Only tables/views released for cloud development (C1) are accessible. Direct access to many standard tables is blocked — use released CDS views instead.
  • (d) False. WRITE and classic lists are not allowed in ABAP Cloud. Use RAP + OData + Fiori instead.
Core principle: In ABAP Cloud, everything must go through released APIs — this is what keeps the core clean and upgrade-stable.
Clean Core~5%

Q12. Distinguish in-app extensibility from side-by-side extensibility. Give a decision criterion.

Show answer
In-app extensibility
  • Runs inside the SAP S/4HANA system (same stack).
  • Tools: Custom Fields and Logic, ABAP Development Tools, RAP extensions.
  • Best for: tight integration with standard objects, transactional logic, field extensions on standard BOs.
Side-by-side extensibility
  • Runs on SAP BTP (separate stack), integrates via APIs/events.
  • Tools: CAP, Kyma, Integration Suite, Event Mesh.
  • Best for: cross-system processes, heavy compute, non-SAP integration, independent lifecycle.
Decision criterion: If the extension must participate in the same transaction and reuse standard BO logic → in-app. If it's decoupled, cross-system, or needs a different runtime → side-by-side.

Q13. Rewrite this to use code pushdown — do the aggregation on the database, not in ABAP.

SELECT * FROM zorder INTO TABLE @DATA(lt_all).
DATA lv_total TYPE p DECIMALS 2.
LOOP AT lt_all INTO DATA(ls).
  IF ls-status = 'C'.
    lv_total = lv_total + ls-amount.
  ENDIF.
ENDLOOP.
Show answer 
SELECT SINGLE SUM( amount ) AS total
  FROM zorder
  INTO @DATA(lv_total)
  WHERE status = 'C'.
Examiner's view: The whole point of pushdown is to send the work to HANA. Using SELECT * then looping is the anti-pattern. Also note: SUM( ) returns NULL if no rows match — wrap with COALESCE( SUM( amount ), 0 ) if you need a guaranteed 0.
ABAP SQL~3%

Q14. What is wrong with this statement, and how do you fix it?

SELECT order_id, customer, amount
  FROM zorder
  INTO TABLE @DATA(lt)
  WHERE amount > 100
  ORDER BY customer.
Show answer
Issue: This is actually valid in modern ABAP SQL (7.40+), but the classic rule was that ORDER BY requires all non-aggregate fields in the select list to be either in the ORDER BY or aggregated. The real trap here is different:
  • If zorder is a client-dependent table, CLIENT SPECIFIED is missing and the client field is auto-added — usually fine, but for cross-client reads you need CLIENT SPECIFIED.
  • Performance: sorting on the DB is good (pushdown), but ensure customer is indexed or the sort happens in HANA anyway.
  • Correct modern form: use a comma-separated field list and INTO TABLE @DATA(lt) — which is what's written. So the statement is syntactically valid.
Better answer: The statement is fine as-is. The examiner is testing whether you know ORDER BY on the DB is preferred over SORT in ABAP, and that @DATA inline declaration is the modern style.

Q15. Design a class hierarchy for a payment processor supporting CreditCard, PayPal, and BankTransfer. Show the interface, abstract class, and factory method. Explain why you'd use a factory.

Show answer 
INTERFACE zif_payment.
  METHODS pay IMPORTING iv_amount TYPE p
              RETURNING VALUE(rv_ok) TYPE abap_bool.
ENDINTERFACE.

CLASS zcl_payment_base DEFINITION ABSTRACT.
  PUBLIC SECTION.
    INTERFACES zif_payment.
    METHODS constructor IMPORTING iv_currency TYPE waers.
  PROTECTED SECTION.
    DATA mv_currency TYPE waers.
ENDCLASS.

CLASS zcl_credit_card DEFINITION INHERITING FROM zcl_payment_base.
  PUBLIC SECTION.
    METHODS zif_payment~pay REDEFINITION.
ENDCLASS.

CLASS zcl_paypal DEFINITION INHERITING FROM zcl_payment_base.
  PUBLIC SECTION.
    METHODS zif_payment~pay REDEFINITION.
ENDCLASS.

CLASS zcl_payment_factory DEFINITION.
  PUBLIC SECTION.
    CLASS-METHODS create
      IMPORTING iv_type     TYPE string
                iv_currency TYPE waers
      RETURNING VALUE(ro)   TYPE REF TO zif_payment
      RAISING   zcx_payment_error.
ENDCLASS.

CLASS zcl_payment_factory IMPLEMENTATION.
  METHOD create.
    CASE iv_type.
      WHEN 'CC'.     CREATE OBJECT ro TYPE zcl_credit_card
                       EXPORTING iv_currency = iv_currency.
      WHEN 'PP'.     CREATE OBJECT ro TYPE zcl_paypal
                       EXPORTING iv_currency = iv_currency.
      WHEN OTHERS.   RAISE EXCEPTION TYPE zcx_payment_error.
    ENDCASE.
  ENDMETHOD.
ENDCLASS.
Examiner's view — why a factory?
  • Decoupling: caller depends only on zif_payment, not concrete classes.
  • Single point of change: adding a new payment type touches only the factory.
  • Testability: easy to inject a mock implementation.
  • Encapsulation: construction logic (currency, config) stays out of business logic.
Design notes: Interface is the contract; abstract class holds shared state (currency). This is the classic Template Method + Factory combination.
